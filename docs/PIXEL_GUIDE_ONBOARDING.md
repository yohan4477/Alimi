# SeoulBeauty 픽셀 한복 가이드 온보딩 — 제품·디자인 명세 (v0.1)

기준 2026-10-19 KST · **사용자가 확정한 방향의 기획안**. 기존 [전략](STRATEGY.md), [서비스 기획](SERVICE_PLAN.md), [디자인 리뷰](DESIGN_REVIEW.md)의 일부. **현재 소비자 웹/iOS 앱에 구현·검증·배포한 기능이 아니다.**

## 목적과 원칙

처음 들어온 사용자가 ‘같은 뷰티 고민을 가진 사람과 실제로 대화한다’는 가치를 빠르게 이해하도록 **작은 2D 픽셀 한복 소녀 가이드**가 손짓·표정·짧은 대사로 도움을 준다. 포켓몬식 튜토리얼의 짧은 발견·환영 감성만 차용한다. 탐색을 미션으로 강제하거나 채팅 대신 캐릭터 육성을 주목적으로 만들지 않는다.

- 기본 의상: 기존 사용자가 고른 **파란색/하늘색 한복 픽셀 캐릭터 1종**. 모바일 기준 시각 표시 높이 약 **80~110px**(화면 폭과 폰트 배율에 따라 조정). 절대로 화면 절반을 덮는 일러스트/복잡한 배경으로 쓰지 않는다.
- 표정·안내: 인사 → 고민 질문 → 추천 발견. 초기에는 정지 이미지와 텍스트 대사, 사용자가 명시적으로 동의하는 가벼운 등장 효과 정도만 검토한다. 동작·진동·사운드·반복 애니메이션은 기본값에서 제외한다.
- 캐릭터는 **서비스 가이드이지 실제 이용자의 개인정보 프로필이나 AI 피부 진단사/의료 상담가가 아니다.** 사용자 아바타 의상과 피부 타입·인종·성별·나이 사이에 자동 연결·추론 없음.
- 한국어/영어는 같은 상태값에 각각의 **완전한 별도 시스템 문자열**을 대응시킨다. 캐릭터 대사·버튼·도움말·에러·빈 상태까지 한 언어만 노출한다. 사용자가 작성한 채팅/고유 상품명은 임의 번역하지 않는다.
- 본인이 언제든 **건너뛰기**, 뒤로가기, 전체 공개 방 탐색, 검색, **자유로운 방 만들기**를 사용할 수 있다. 검색·초대 링크로 직접 진입한 사람에게는 온보딩이 목적 화면을 가리지 않게 한다.

## 3단계 시나리오 (최초 방문자가 선택하거나 바로 둘러보기)

| 단계 | 가이드 대사 KO / EN (초안) | 화면 구성·행동 | 분기·예외 | 측정 제안 |
|---|---|---|---|---|
| 1. 인사 + 분야 선택 | “안녕! 어떤 뷰티 이야기가 궁금해?” / “Hi! What beauty topics are you curious about?” | 작은 한복 소녀 + 'Skincare'·'Makeup' **각각 ON/OFF, 둘 다 가능**. [다음] [먼저 둘러보기]. 처음부터 피부 타입/성별/나이 질문 금지 | 스킨만/메이크업만/둘 다/미선택. 한쪽만 골라도 진행, 0개면 전체 탐색 안내. 기기 언어 기본값·수동 전환 | 첫 노출→다음, 스킵, 분야별/동시 선택, 언어별 이탈 |
| 2. 세부 고민 선택 | “요즘 어떤 게 제일 궁금해?” / “What would you like to talk about?” | 선택한 분야의 고민 **각각 복수 선택**. 스킨: 트러블·민감성·건조·모공. 메이크업: 쿠션 호수·틴트·지속력·베이스 등. [친구 찾기] [뒤로] [건너뛰기] | 선택을 해제하거나 이전 단계로 돌아가도 손실 없음. 관심 분야를 끄면 그 분야의 고민 태그 추천 제외. 피부 타입/톤은 이후 선택형 정보 | 고민 선택/완료·이탈, 조합별 스킵, 돌아가기 |
| 3. 추천 발견 + 입장 | “찾았다! 여기서 같은 고민을 이야기하고 있어!” / “Found some conversations you might like!” | 현재 존재하는 **실제 공개 채팅방**의 고민 일치 이유·최근 실제 활동/질문 미리보기. [대화 읽기]와 [전체 방 보기] [방 만들기] 병렬 진입 | 관련 방 없음 → 인기/새 대화·검색·자유 방 만들기. 참여자가 없는 곳을 가짜로 추천하지 않음. 방에 들어간 후 가이드 축소/퇴장, 실제 사용자 대화를 가리지 않음 | 추천 노출→입장, 첫 열람→첫 실제 메시지, 생성/검색 경로·D7 |

### 실제 화면 배치

1. 상단 제품 워드마크·진행률 (1/3 등) 및 언어 버튼. 아래 가이드 캐릭터 **작은 도트 이미지(대략 80~110px)** + 짧은 말풍선 1개. 나머지 화면은 선택칩과 명확한 다음 CTA가 차지한다.
2. 긴 게임 장면·시차 큰 등장 애니메이션·레벨/보상/몬스터를 넣지 않는다. 입력 내용을 ‘피부 진단 결과’로 표기하지 않는다.
3. 추천 화면에만 작은 발견 표현을 허용하지만 수치 근거 없는 “99% 매칭”과 인위적 활동 숫자를 만들지 않는다.
4. 온보딩 종료 시 기존 커뮤니티 UI로 전환한다. Community / Search / My Activity 탭과 게시글/실시간 채팅·상품 카드·가격 추적 제외 정책을 보존한다.

|---|---|---|

| 미션·레벨업·새 옷 잠금 해제 | 첫 대화와 답변 유용성을 왜곡할 수 있어 초기 미도입 | 보류 |

**보유한 시안 자산**: 대화에서 제작한 480×720px 투명 PNG 10종(예: `한복_하늘색.png`, `한복_분홍색.png`, `한복_보라색.png`, `한복_민트색.png`, `한복_금색.png`; 나머지 5개는 연예인 이름이 파일명으로 지정된 패션 시안). 앱 배포 자산에 자동 업로드된 것으로 간주하지 않는다. 공개 앱에서 연예인 실제 협업·공식 의상으로 오인되지 않게 이름과 표현·권리 확인이 필요하다.

## 로딩 중 캐릭터 교체 — 디자인 리뷰 반영

**요청 확정:** 온보딩 중뿐 아니라 **실제 데이터 로딩**에서도 작은 캐릭터를 표시하고, 여러 옷의 캐릭터가 **번갈아 등장**한다. 캐릭터 순환을 위해 시간을 고의로 지연시키거나 가짜 진행률을 표시하지 않는다.

| 대기 상황 | 캐릭터 동작 · 대사 | 레이아웃/가드레일 |
|---|---|---|
| 0~400ms 짧은 대기 | 기존 텍스트/스피너만. 캐릭터는 미표시 | 빠른 응답을 시각적으로 방해하지 않음 |
| 400ms 이상 지속되는 대기 | 2D 픽셀 의상 캐릭터 등장, 실제 작업을 나타내는 KO/EN 로딩 문구 유지 | 캐릭터는 화면 중앙/목록 내 작게, 콘텐츠와 입력을 가리지 않음 |
| 계속 로딩 중 | 동일 캐릭터 기본 복장의 외형을 유지하면서 **10종 의상 순서대로 약 2.2초 간격** 전환(한복 5종 + 스테이지 패션 5종) | 1장의 5×2 경량 스프라이트(약 4.8KB) 캐시. 한 번에 10장 네트워크 호출 안 함. 스크린리더는 상태 텍스트 한 번만 읽음 |
| 데이터 도착 | 즉시 로더 제거, 본래 화면 표시 | 캐릭터 전환 주기나 최소 노출시간이 완료를 지연하지 않음 |
| 오류/시간 초과 | 캐릭터 무한 재생 대신 오류 문구 및 재시도/둘러보기 경로 제공 | 완료된 데이터를 숨기지 않으며 재시도는 실제 요청 재호출 |
| 모션 줄이기 / 앱 백그라운드 | 순환을 중단하고 첫 한복 캐릭터 1종을 정적으로 유지 | iOS 접근성 Reduce Motion / 웹 prefers-reduced-motion 지원 |

**디자인팀 검토 결론(휴리스틱, 사용자 실험 아님):** 캐릭터를 '대기 화면의 동반자'로 쓰는 것은 일관된 브랜드 경험에 도움이 될 수 있지만, 로딩 시간을 길게 느끼게 하거나 대화 작성 중 시선을 빼앗으면 역효과다. 메시지 전송, 채팅 읽기/입력, 실시간 타이핑과 겹치지 않게 하고 기존 로딩 위치(커뮤니티 첫 열기, 게시글/채팅 기록, 브랜드·상품 데이터 탐색)에만 붙인다. 이미지 그 자체는 피부/성별/나이 데이터 수집과 무관하다.

**익명 의상 식별:** 내부 프레임 순서만 사용하고, 아이돌 이름은 UI/분석 이벤트/이미지 alt에 포함하지 않는다. 유명 연예인 공식 의상/협업으로 표시하지 않는다. 공개 유통 전 영감이 된 원본·표현·권리 확인이 필요하다. 이후 사용자 아바타 선택(P1)과 별개이며 로딩 중 의상이 곧 본인의 프로필이 되지 않는다.

**현재 구현 범위(별도 CI 검증 필요):**
- 웹: `dist/loading-companion.js`, `dist/style.css`, `dist/app.js`, `dist/chat.js`에서 실제 비동기 로딩 컨테이너에 한정해서 적용. CSS만으로 단계별 10종 순환, 로딩 완료 즉시 DOM 제거, reduced motion에서 정지.
- iPhone: `ios/Alimi/LoadingCompanion.swift`, 웹과 같은 10종 스프라이트를 Xcode asset catalog에 등록하고 실제 데이터 요청용 `ProgressView` 일부를 대체. 빠른 요청은 기본 진행 표시 유지, 로딩이 계속될 때만 캐릭터 표시. iOS 실기기·TestFlight/운영 배포 검증은 별개.
- 원본 10개 전체 해상도 PNG 파일은 여전히 대화 아티팩트에 있으며 이번 구현은 **로딩 전용 축소 스프라이트**만 앱에 포함한다. 원본을 앱의 프로필 아바타로 자동 등록하지 않는다.

**추가 검증 지표(제안·미측정):** 캐릭터 노출 조건이 충족된 요청 비중, 로딩 완료/실패·재시도, 대기 시간의 p50/p95, 무한 로딩, 이탈·첫 대화 참여율, 접근성·리소스 비용. 캐릭터의 노출을 늘리려고 로딩 시간을 늘리면 안 된다.

## 개발/QA 수용 기준 (디자인·개발 협업용)

- [ ] 한국어/영어 전 단계 및 에러·복귀·건너뛰기 문구 점검. 고객 작성 원문은 유지.
- [ ] 첫 단계에서 스킨케어·메이크업 둘 다 선택 가능, 각각의 복수 고민 저장/해제 정확.
- [ ] 입력값 없이 스킵해도 기존 전체 공개 채팅방·검색·자유 생성 진입 가능.
- [ ] 같은 고민 추천은 **현재 실제 존재하는 방/활동** 근거. 방 부족·오프라인·권한 오류·로딩/재시도 분기 존재.
- [ ] 최초 진입 시 단 한 번 제안, 이후 My Activity에서 다시 설정 가능. 초대·검색 딥링크 차단 금지.
- [ ] 캐릭터를 비활성화하거나 모션 줄이기 설정에서도 온보딩 사용 가능. 스크린리더용 대체설명(“인사하는 한복 소녀”)과 접근 가능한 터치 영역, 320/390/1024px 레이아웃 검증.
- [ ] 피부·메이크업 고민 값은 최소한의 추천용 정보로만 취급; 공개 프로필 자동 게시, 인종·나이·성별 추정, 민감값의 광고 추적 전달 금지.
- [ ] 사용자 작성 글·게시글/채팅·상품 카드·원래 대화로 돌아가기 및 제휴 고지는 그대로 동작.

## KPI·실험 가설

- **북극성(선행)**: 신규 이용자 첫 유의미 참여율 = 정해진 관찰 기간 내 첫 질문/댓글/실제 채팅 메시지를 남긴 신규 이용자 / 해당 기간의 신규 이용자. **최종 수익 KPI는 승인·귀속된 순제휴 수수료**로 유지.
- **퍼널**: 가이드 노출 → 분야 선택 또는 스킵 → 고민 선택 또는 스킵 → 추천/탐색/방 생성 진입 → 실제 대화 열람 → 첫 유의미 참여 → D7.
- **실험**: 동일한 관심사 선택/채팅방 추천 UI에 대해 *캐릭터 가이드 있음 vs 없음*을 비교해 캐릭터 자체의 효과를 분리한다. *온보딩 우선 vs 커뮤니티 우선* 실험은 다른 축으로 별도 설계한다. 두 변수를 한 실험에 섞지 않는다.
- **성공 신호**: 첫 읽기율과 실제 첫 발화율 개선; 온보딩 완료율만 좋아지고 대화가 늘지 않으면 성공으로 판정하지 않는다.
- **가드레일**: 단계별 이탈·스킵률, 가이드 로딩/접근성 문제, 첫 유용한 답변 시간, 무응답 질문·신고, D7. 외모 등급·캐릭터 레벨/보상과 사용자 참여 품질을 연결하지 않는다.
- **데이터 최소화**: 개인의 피부 고민·아바타 의상 정보를 원시 분석 이벤트에 담지 않고, 이용 흐름 분석에 필요한 단계·언어·플랫폼·비식별 선택 조합 수준만 수집 여부와 동의를 검토한다.

## 변경 범위·현황

**온보딩 가이드 자체는 기획문서·관리자 시안이며 실제 소비자 온보딩 미구현**이다. 별도로 이번 요청의 **실제 비동기 로딩에 캐릭터를 보여주는 웹/iOS 코드와 소형 자산을 추가**했다. 이 코드의 최종 CI/실기기/운영 배포 결과는 아직 미확인이다. 추천 알고리즘·온보딩 데이터 저장·분석 이벤트는 기존 상태 유지. 실제 구현 여부는 [관리 대시보드](PRODUCT_STATUS.md)와 GitHub 이슈/PR 근거로만 갱신한다.

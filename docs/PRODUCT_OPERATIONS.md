# 제품 운영 규칙

## 원장과 갱신 책임

- Issue: 기능별 문제·가설·상태·검증 기준·차단 요인·실행 이력의 원장.
- PRODUCT_VISION: 사업 방향. ROADMAP: 선행 관계. DECISIONS: 승인과 변경 이유.
- FEATURE_REGISTER: 기능 ID와 Issue의 고정 매핑. PRODUCT_STATUS: 날짜가 있는 현황 스냅샷.
- 제품 책임자 John Choi가 개발/출시 승인을 기록한다. 작업 담당자는 실행과 증거를 기록하고 문서 PR을 만든다. 담당자가 정해지지 않은 일은 '미배정'으로 적는다.
- 문서와 Issue가 충돌하면 최신 근거와 상태 변경 기록을 대조하고 정정한다. 무조건 최신 문구나 높은 상태를 채택하지 않는다.

## 상태 전이

| 상태 | 진입에 필요한 증거 | 다음 단계 조건 |
|---|---|---|
| 아이디어 | 문제·대상·가설 및 출처 | 중복 확인, 검증 범위/담당자/기준 확정 |
| 검증 예정 | 계획 승인, 표본·기간·성공/실패 기준, 실행 담당자 | 실제 검증 시작 기록 |
| 검증 중 | 인터뷰/PoC/사용성 등 실제 실행 기록 | 결과와 불확실성 기록 후 개발 여부 결정 |
| 개발 승인 | 승인자·날짜·Issue/결정 링크, 범위·의존성 충족 | 구현 브랜치·작업 시작 |
| 구현 중 | 관련 코드 커밋/PR 및 남은 작업 | 기능별 수용 기준 검증 실행 |
| 검증 완료 | 승인 범위의 구현과 모든 필수 테스트 통과, 환경·커밋·결과 | 별도 출시 승인 및 실제 공개 증거 |
| 출시 | 배포 버전·대상·시각·배포 링크 및 출시 후 확인 | 회귀 시 상태/차단 사유 재평가 |

기본 흐름: 아이디어 → 검증 예정 → 검증 중 → 개발 승인 → 구현 중 → 검증 완료 → 출시. 구현 후 수용 테스트는 구현 중에 수행한다. 실패하면 해당 상태를 유지하고 차단 기록 또는 이전 단계로 되돌리는 이유를 남긴다. 검증 중 단계는 개발 전 가설/PoC 검증이며 검증 완료와 다르다.

**기존 MVP 이관 예외:** 이미 코드와 일부 테스트가 있으나 과거 승인 기록을 이번에 소급 생성하지 않는다. ALM-001/F1–F5는 '검증 중(기존 구현 이관)'으로 시작한다. 실기기 게이트와 제품 책임자의 범위 확인 후 검증 완료로 이관할 수 있으며, 순서 예외와 근거를 상태 이력에 명시한다. 수정 개발이 필요하면 별도 개발 승인→구현 중으로 이동한다.

차단/보류는 별도 속성이다. 필수 7개 상태에 임의 상태를 추가하지 않는다. 실패 원인, 의존 Issue, 해제 조건, 다음 확인 담당자를 기록한다. Issue 닫힘은 출시의 증거가 아니며 중복/보류 종료 이유를 구분한다. 진행률 백분율을 추정하지 않는다.

## 대화에서 개발로 연결하는 절차

1. 새 대화 시작 시 README→현황→관련 Issue/댓글→DECISIONS→최신 main/PR/Actions를 확인한다.
2. 대화에서 신규 아이디어와 결정·질문을 분리한다. 저장 요청 또는 이 관리 체계 운영 요청에 따라 기록하되 단순 아이디어를 개발 승인으로 해석하지 않는다.
3. 열린/닫힌 Issues를 기능 ID, 한글/영문 동의어, 해결 문제로 검색한다. 기존 범위면 원문 보존 후 갱신; 범위가 다르면 새 ID를 할당하고 관계를 연결한다.
4. 기능 템플릿의 필수 정보를 모두 기록한다. 미구현·미실행·미정은 빈칸 대신 명시한다. 새 기능 ID는 FEATURE_REGISTER 최댓값 다음을 사용하고 기존 ID를 재사용하지 않는다.
5. 최소 검증 계획과 성공/실패 기준을 제안한다. 승인 근거 없이 개발 승인으로 올리지 않는다.
6. 구현 PR에는 Issue·기능 ID·범위·테스트 근거·미확인 항목을 연결한다. 증거는 commit SHA, 환경, 명령/시나리오, 예상/실제 결과, 일시를 포함한다.
7. 작업 종료 시 Issue 원장, FEATURE_REGISTER 매핑, ROADMAP 의존성, PRODUCT_STATUS 스냅샷을 갱신하고 의사결정 변화는 DECISIONS에 추가한다.
8. 사용자에게 생성/변경 링크와 미완료를 보고한다. main 병합은 승인 후 진행한다.

모든 ChatGPT 대화가 자동으로 이 저장소에 동기화되는 기능은 없다. 대화 종료 때 저장소 반영을 실행한 경우에만 보존된다. 다음 호출 예: “Alimi 제품 현황과 이슈를 읽고, 이번 아이디어를 중복 확인 후 기록해. 개발 승인은 별도로 남겨.”

## 검증 기록

[검증 양식](validation/TEMPLATE.md)을 복사한다. '통과'는 원시 결과/로그 링크가 있어야 한다. 가상/실제 데이터, 단위/UI/실기기, APNs 수락/실제 수신, 실험/출시를 구별한다. 만료되는 Actions artifact만 유일 근거로 두지 말고 비밀정보를 제거한 결과 요약을 docs/validation에 보존한다.

## GitHub Projects (미생성)

현재 연결 도구에는 Projects v2 조회/생성/필드 편집 기능이 없고 로컬 gh도 없다. 기존 보드 유무·권한은 확인하지 못했다. 생성된 보드가 있다고 보고하지 않는다. 문서 현황+Issues를 즉시 사용한다.

추후 권한/도구 확보 시 기존 보드 검색 후 없을 때 'Alimi Product' 보드를 만들고 기존 Issues를 추가한다(새 Issue 복제 금지).
필드: 기능 ID, 제품 상태(위 7개), 우선순위(P0/P1/P2/장기), 대상, 차단 여부/사유, 선행 Issue, 담당자, 다음 행동, 최근 근거 URL, 갱신일.
뷰: 현재(P0/검증 중/구현 중), 차단, 다음(P1/P2), 장기(아이디어), 최근 검증 완료/출시. 기본 Done을 검증 완료·출시로 자동 대응하지 않는다. 자동 종료/출시 전이는 설정하지 않는다.

## 브랜드 표기

사용자 결정(2026-10-16): 브랜드명은 항상 **Alimi**로 쓴다. 문서, UI 로고, 화면 제목, 접근성 문구, 페이지 제목과 소개 문구에 적용한다. 기존 URL, 번들 ID, 저장 키, 코드 식별자와 파일 경로는 호환성을 위해 유지한다. 과거 검증 스크린샷은 당시 실행 증거이므로 소급 편집하지 않는다.

# Alimi 기획박스 (Idea Inbox)

**역할:** 자유롭게 던진 기획을 잃지 않고 보존하는 임시 수집 공간. 공식 기능 상태·진행 이력의 원장은 [GitHub Issues](https://github.com/yohan4477/Alimi/issues)이며, 이 문서는 별도의 개발 백로그나 출시 약속이 아니다.

[운영 규칙](PRODUCT_OPERATIONS.md) · [기능 인덱스](FEATURE_REGISTER.md) · [로드맵](ROADMAP.md) · [현황판](PRODUCT_STATUS.md)

## 기록 트리거 — 사용자가 명시적으로 요청할 때만

- 사용자가 Alimi 아이디어를 말하고 **“기획박스에 넣어”**, **“기획박스에 넣을게”**, **“기획박스에 저장해”**, 또는 **“공급 박스에 넣어”**라고 요청하면 해당 아이디어를 GitHub에 보존한다. “공급 박스”는 별도 저장소가 아니라 **기획박스의 공급자 분야**를 뜻하는 명령어 별칭이다.
- 기록할 아이디어가 앞선 대화에 명확하면 별도 재확인 없이 진행한다. GitHub 접근이 불가능하거나 대상이 불분명할 때만 제약을 보고한다. 저장 성공은 실제 GitHub 쓰기 결과를 확인한 후 알린다.
- 메시지에 기획 내용이 없으면 어떤 내용을 기록할지 먼저 확인한다. 별도의 명시적 요청 없이 모든 대화를 자동 동기화한다고 주장하지 않는다.
- 표현이 미완성·모순되거나 검증되지 않아도 원래 취지를 유지한다. AI의 해석과 제안은 *별도* 표시한다.
- 우선 같은 기능의 Issue와 이전 기획박스 항목을 검색한다. 중복이면 **기존 항목에 추가하거나 링크로 연결**한다. 새 이슈를 무조건 발행하지 않는다.
- 자유 기획만으로 우선순위·개발 승인·로드맵·코드를 바꾸지 않는다. 사용자가 **“검증 계획으로 승격”**, **“개발 승인”** 등으로 별도 요청하면 [운영 규칙](PRODUCT_OPERATIONS.md)의 증거·승인 조건을 따른다.
- 저장 후에는 변경 파일/Issue 링크, 분류 결과, 미확정 사항을 보고한다. 기본적으로 작업 브랜치와 PR로 제출하고 기존 운영 규칙에 따라 main 병합은 별도 승인 후 진행한다.

## 현재 수집 대기

### BOX-20261015-001 — 화장품 가격 급락 발견·신뢰 표시·상품군별 구매 검증

- **입력일:** 2026-10-15 (KST)
- **원문 / 사용자가 표현한 생각:** “가격 변동이 큰걸 알려주는 건 어떨까?”, “내 관심 대상이 아닌데 충동 구매를 유발하게 하는거야”, “가장 중요한건 신뢰성이야”, “내 상품군은 화장품이잖아. 단공상품이 있을거고 반짝 뜨는 상품도 있을거고”, “이런거 어떻게 검증하지?”
- **구분:** 소비자 / 상품 발견·전환 / 신뢰 / 검증
- **핵심 문제와 가설:** 기존 관심 상품 알림 외에, 원래 관심 없던 화장품도 실제 가격 혜택과 유행을 통해 발견하고 구매하게 한다. 신뢰성이 최우선이다. 구매 증가 효과는 미검증 가설.
- **관련 기능 / GitHub Issue:** [가격 이력 #4](https://github.com/yohan4477/Alimi/issues/4), [총액 비교 #5](https://github.com/yohan4477/Alimi/issues/5), [실제 가격 수집 #8](https://github.com/yohan4477/Alimi/issues/8), [실사용자 실험 #11](https://github.com/yohan4477/Alimi/issues/11), [제휴 #12](https://github.com/yohan4477/Alimi/issues/12), [글로벌 비교 #13](https://github.com/yohan4477/Alimi/issues/13), [SNS 발견 #1](https://github.com/yohan4477/Alimi/issues/1).
- **기존 기능과 관계:** 가격 기회 기반 발견은 신규 아이디어이며 기존 가격·비교·실험 기능과 연결. SNS 콘텐츠에서 상품을 찾는 #1과 구별하되 연계 가능. 중복 기능 Issue는 발행하지 않음.
- **상태:** 수집됨 (개발 미승인). 구현·사용자 실험 미실행. 정식 기능 ID·우선순위·일정 미정.
- **다음 처리:** 검증 계획 초안 보관. 타깃·상품 분류 정의·데이터 확보·측정 가능성 확정 후 승격 검토.
- **미확정 표현:** 사용자 “단공상품”을 대화에서 AI가 스테디셀러/단골 구매 상품으로 해석했으나 확정되지 않음. 원문을 보존하고 아래 분류는 잠정안으로 취급.
- **추가 메모와 변경 이력:** 2026-10-15 — 사용자 명시적 저장 요청으로 이 대화의 아이디어·신뢰 원칙·검증 제안을 함께 수집. 저장는 개발·실험 승인과 별개.

#### AI 구조화 제안 — 발견 화면과 상품군 (미확정)
- “오늘의 급락”: 관심 상품 등록 없이 열람. 단순 변동성보다 현재 실제 하락과 절약액, 가격의 희소성, 구매 가능한 조건을 표시.
- “쓰던 제품, 지금 싸게”: 스테디셀러 재구매/쟁여두기.
- “요즘 눈에 띄는 제품”: 최근 뜨는 상품의 발견/첫 구매. 유행 출처·관측 기간·협찬 여부 표시.
- 신상품은 별도 후보로 취급하고 부족한 가격/사용 이력을 명시. 유행→스테디셀러 전환은 시간에 따라 관찰.
- 초기 수동 큐레이션과 UI 검증부터 시작. 인기와 효능·개인 피부 적합성을 동일시하지 않음.

#### AI 구조화 제안 — 신뢰 표시
1. 판매자 정가보다 최근 실제 관측가격 중앙값을 비교 기준 후보로 사용. 기간·관측 빈도·판매처 범위·동일 옵션 정의를 함께 확정.
2. 가격 그래프, 추적 기간·판매처 수, 마지막 확인 시각, 재고 확인 여부 제공. “추적한 90일 중 최저”, “비교한 5곳 중 최저”처럼 범위를 한정.
3. 배송비·세금 등 총액과 쿠폰/회원/카드 조건 구분. 미확인 비용이 있으면 완전한 실구매가라고 표시하지 않음.
4. 용량·수량·세트·리뉴얼·사용기한 조건 확인. 사용기한 미확인은 명시. 단위가격과 결제 총액을 구별.
5. 가격 인상 후 할인하는 패턴을 장기 이력으로 점검. 자료 부족 시 할인/최저가 배지 보류.
6. 판매자 신뢰·정품·반품 조건은 가격 신뢰와 분리. 수수료 공개, 광고 구분, 수수료로 할인 순위를 왜곡하지 않음.
7. “가격이 달라요” 신고·재검수·오류 상품 노출 보류. 허위 희소성/마감 표시 금지.

#### AI 검증 초안 — 아직 실행하지 않음
**1) 상품/운영 PoC:** 스테디셀러·최근 유행 × 평소 가격·실제 할인 2×2 그룹. 그룹당 약 5개는 운영 점검 제안이며 통계적 충분 표본이 아님. 같은 카테고리·비슷한 가격대와 구매 조건을 맞춤. 서로 다른 상품 비교는 브랜드·선호 차이가 남으므로 할인/유행의 인과효과로 단정하지 않음.

**2) 화면 이해:** 타깃 국가 하나 선정 후 화장품 구매자 5~8명 사용성 인터뷰 제안. 사고 싶은 상품 선택, 저렴하다고 판단한 근거, 추가 확인사항, 기존 인지/구매/관심을 질문. 호감 응답은 구매 증거가 아님.

**3) 실제 전환:** 노출→상세→판매처 이동→확인된 주문→취소/반품 제외 주문→재방문/재구매를 분리. 핵심은 기존 구매 의향이 없던 상품의 확인된 구매와 방문자당 순제휴 수익. 미등록을 무관심으로 간주하지 않고 기존 의향을 별도 확인. 동의 기반 제휴 전환 또는 구매 확인으로 측정하며 클릭만 있으면 구매 미검증.

**4) 신뢰 표시 실험:** 동일 상품·가격에서 필수정보가 명확한 A와 동일 정보에 이력·근거·확인 시각을 더 눈에 띄게 제시한 B를 사용자 단위 무작위 배정. 필수 조건은 양쪽에 공개. 전환·가격 일치율·조건 오해·신뢰 응답을 함께 비교.

**5) 성공/실패 판단:** 기준 전환율·최소 의미 있는 개선폭·표본·기간·취소/반품 관찰기간·가격 일치 허용기준은 실행 전에 확정. 가격 일치율은 확인 가능한 결제 조건 대조 건수와 미확인 비율을 같이 보고. 표본 부족은 결론 유보. 신뢰 악화나 가격 오류를 구매 증가로 상쇄해 성공 처리하지 않음. 재구매는 상품 소비 주기에 맞춘 후속 관찰 필요.

## 분류와 승격

1. **수집:** 아이디어 그대로 남긴다. 구현과 비용 발생 작업은 하지 않는다.
2. **정리:** 기존 Issues·결정 기록·기능 ID와 비교해 관계를 연결한다.
3. **검증:** 필요할 때 사용자의 지시로 가설·표본·성공/실패 기준을 갖춘 검증 계획으로 이동한다.
4. **개발:** 승인자·범위·근거·의존 조건을 충족한 Issue만 개발 단계로 이동한다.
5. **환류:** 검증 실패, 방향 변경, 포기 이유도 지우지 않고 연결한다.

> **중요:** 단순 기획 수집은 개발 작업이나 실제 사용자 테스트가 아니다. 기획박스의 항목 수를 출시 기능이나 진척률로 계산하지 않는다.
